# セキュリティ

## 基本的な考え方

- **木を見て森を見ずにならない。** 個々の対策だけでなく、システム全体を俯瞰する。
- **多層防御を意識する。** 1つの対策が突破されても、ほかの層で攻撃の影響を抑える。
- 最初に資産や通信経路を**棚卸し**し、現状の対策と**あるべき姿**との差分、および侵害時の**影響度**を確認する。

> **2つの「7分類」は別物。** 以下の「守るべきもの7つ」は、LGWANのセキュリティを点検するための整理。後半の「7層の多層防御」は添付画像に示された防御レイヤーの整理。1対1に対応する分類ではない。

## 守るべきもの7つ（セキュリティ点検領域）

### 1. データ

#### 棚卸し

- [ ] LGWANが保持しているすべてのデータを洗い出す。
- [ ] 全サーバーの保存先ディレクトリを洗い出す。
- [ ] DBがある場合は、DB内のデータも洗い出す。
- [ ] ユーザーごとに使用するディレクトリが異なるか確認する。

#### 対策（あるべき姿）

- [ ] 保存データが暗号化されている。
- [ ] 転送データが暗号化されている。
- [ ] バックアップを取得している。
- [ ] 必要な人・プロセスだけがアクセスできるように制御している。

#### 影響度

- [ ] データが漏洩した場合の影響を評価する。

### 2. アカウント・ID

#### 棚卸し

- [ ] 各サーバーへのログイン方法を把握する。
- [ ] 各サーバーに存在するユーザーを洗い出す。
- [ ] 各ユーザーのログイン方法（認証方式、鍵、パスワード）を確認する。
- [ ] 各ユーザーに付与されている権限を確認する。
- [ ] APIキーを扱っているか確認する。
- [ ] 認証情報・鍵・パスワードの管理方法を確認する（「7. 開発・運用プロセス」とも関連）。

**キーワード：** パスワード、ユーザー、認証、権限、キー

#### 対策（あるべき姿）

- [ ] 多要素認証（MFA）の適用可否・適用状況を確認する。
- [ ] 最小権限の原則を適用している。
- [ ] 弱いパスワードや使い回しを防ぎ、適切な場所・方法で管理している。
- [ ] 鍵・パスワードの更新／ローテーション方針がある。

#### 影響度

- [ ] サーバーやユーザーアカウントへの不正アクセスが起きた場合の影響を評価する。

### 3. 通信・ネットワーク

#### 棚卸し

- [ ] すべての通信経路・接続先・使用ポート・通信プロトコルを洗い出す。
- [ ] 各通信に対して以下の対策が適用されているか確認する。

#### 対策（あるべき姿）

- [ ] TLSを使う通信ではTLS 1.2以上を採用し、適切に暗号化している。
- [ ] 対象となるWeb通信にWAFを導入している。
- [ ] ファイアウォールで不要なポートを閉じている。
- [ ] ネットワークを適切にセグメント分離している。
- [ ] 内部サービス間の通信でVPN／プライベートネットワークを使用するなど、不要なパブリックインターネット経由を避けている。
- [ ] 内部ネットワークであっても信頼を前提とせず、リソースへのアクセスを認証・認可する（ゼロトラスト）。
- [ ] 証明書の有効期限を監視し、更新方法（可能なら自動更新）を整備している（「7. 開発・運用プロセス」とも関連）。

#### 影響度

- [ ] 通信を盗聴された場合の影響を評価する。
- [ ] 通信を改ざんされた場合の影響を評価する。
- [ ] 通信相手になりすまされた場合の影響を評価する。
- [ ] そのほか、通信の遮断・不正接続・横展開などによる影響を確認する。

> **補足：** TLSは適用可能なプロトコルで使う。WAFは主にHTTP/HTTPS通信向けの対策であり、すべての通信を保護するものではない。

### 4. アプリケーション

#### 棚卸し

- [ ] 各アプリケーション・APIについて、以下の対策の実施状況を確認する。

#### 対策（あるべき姿）

- [ ] フロントエンドとバックエンドの双方で入力バリデーションを実施する（フロント側だけでは回避される）。
- [ ] SQLインジェクション、XSS、コマンドインジェクションへの対策を実装する。
- [ ] セキュアコーディングガイドラインを徹底する。
- [ ] SAST／DASTなどのセキュリティテストを自動化する。
- [ ] 依存ライブラリを把握・管理し、脆弱性を定期的にスキャンする。
- [ ] 適切なエラーハンドリングを実装し、スタックトレースや内部情報をユーザーへ表示しない。
- [ ] Content Security Policy（CSP）を設定し、XSSの影響を低減する。

> **補足：** 入力バリデーションだけで各種インジェクションを完全に防げるわけではない。SQLのパラメータ化、出力のエスケープ、OSコマンドの安全な実行方法なども必要。

### 5. インフラ・サーバー

#### 棚卸し

- [ ] 使用しているOSを洗い出す。
- [ ] 使用しているミドルウェアを洗い出す。
- [ ] 各サーバーで以下の対策が実施されているか確認する。

#### 対策（あるべき姿）

- [ ] パッチ管理：OSやミドルウェアの脆弱性に対して、リスクに応じて速やかにセキュリティパッチを適用する。
- [ ] CSPM：クラウド設定のミスを継続的に検出・修正する（クラウド利用時）。
- [ ] 構成ドリフトを防止・検出する。イミュータブルインフラストラクチャによる再作成方式も検討する。
- [ ] コンテナセキュリティ：ベースイメージの脆弱性スキャン、最小権限での実行、読み取り専用ファイルシステムなどを適用する（コンテナ利用時）。
- [ ] CISベンチマークなどに基づくセキュリティベースラインをOS・クラウド設定へ適用する。
- [ ] 不要なサービスやポートを無効化する。

#### 影響度

- [ ] 不正アクセス、マルウェア感染、情報漏洩、サービス停止などの影響を評価する。

### 6. サービスの可用性

#### 棚卸し

- [ ] 以下の可用性対策の実施状況を確認する。

#### 対策（あるべき姿）

- [ ] DDoS対策：大量リクエストの吸収やフィルタリングを行う。
- [ ] 冗長化・フェイルオーバー：単一障害点（SPOF）をなくし、障害時に切り替えられるようにする。
- [ ] レートリミット：APIへの過剰リクエストを制限する。
- [ ] インシデント対応計画：エスカレーションフローや復旧手順を文書化する。
- [ ] モニタリングとアラート：異常なリクエスト増加などを検知する。
- [ ] 災害復旧（DR）訓練：定期的に復旧テストを実施する。

#### 影響度

- [ ] サービス停止が発生したときの影響を評価する。

### 7. 開発・運用プロセス

#### 棚卸し

- [ ] 以下の開発・運用上のセキュリティ対策の実施状況を確認する。

#### 対策（あるべき姿）

- [ ] CI/CDパイプラインにSAST、DAST、依存関係スキャンを組み込む（アプリケーション）。
- [ ] IaCテンプレートを静的解析する（インフラ）。
- [ ] シークレット管理ツールでパスワードや鍵などを一元管理する。
- [ ] SBOMを管理し、新たなCVEが公開された際に影響を把握・対応できる継続的な監視の仕組みを整える。

## 7層の多層防御（添付画像の整理）

![7層の多層防御。物理セキュリティ、IDとアクセス、境界、ネットワーク、コンピューティング、アプリケーション、データの7層](./assets/security-seven-layers.svg)

| 層 | 分類 | 対象例 |
| --- | --- | --- |
| 7 | データ（Data） | 保存情報、機密情報、バックアップ |
| 6 | アプリケーション（Application） | Webアプリ、API、ソースコード |
| 5 | コンピューティング（Compute） | OS、サーバー、仮想マシン、コンテナ |
| 4 | ネットワーク（Network） | 通信経路、ファイアウォール、セグメント、TLS |
| 3 | 境界（Perimeter） | 外部との接続点、DDoS対策、WAF |
| 2 | IDとアクセス（Identity & Access） | アカウント、認証、認可、MFA |
| 1 | 物理セキュリティ（Physical Security） | データセンター、設備、物理アクセス |

**ポイント：** どれか1層だけに依存せず、複数の層で防御する。なお、上記の「サービスの可用性」「開発・運用プロセス」は、これらのレイヤーを横断する観点。

## 「自分の意見」

上記ではサービス単位であるべき姿を記している。

組織単位で見たときに、各サービスのリスクで判断せず、重大な脆弱性は一律で対応するべきという考え方(ガバナンス)。それはそれで納得。

→上記を根本知識として持ちながら、実際の運用(急を要する脆弱性にはリスク関係なく対応させられる)ことを考えて、その上であるべき姿を描く。

脆弱性は、確実に穴があることが分かるから話題にされるけど、他のセキュリティ面もサービスに委ねられているだけでちゃんと対策できてないのもあるのでは？

上記を全部対策してるっていう確認はなんの項目でやってる？

**手動変更は絶対にさせない！！！**

→手動設定、変更の操作がないか確認

対策をやりっぱなしにしない。

継続的な運用まで含めて構築が必要。

→CI/CD(マスター)と連携して
SBOM作成や検査などを実施

というかむしろそこの運用方法を考える。
